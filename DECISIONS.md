# DECISIONS

Журнал проектных решений. Начальное наполнение — раздел 2 спецификации `2026-10-24-common-protocol-design.md` (D-01…D-20); затем — решения реализации.

## Решения спецификации

| ID | Решение | Причина |
|---|---|---|
| D-01 | Один репозиторий, src-layout, 5 пакетов: общий `expcore` + `photometric`, `geometric`, `metric`, `experiments`. Общий пакет назван `expcore`, а не `common` | ОБЩ-01; общее имя `common` часто конфликтует с другими пакетами в окружении |
| D-02 | Все разбиения используют `np.random.Generator(np.random.PCG64(2026))`, **новый генератор на каждую независимую операцию** (KADID; HPatches-`i_`; HPatches-`v_`; каждая категория MVTec; SOP) | ТЗ называет PCG64 явно для MVTec/SOP, для KADID/HPatches — только `seed=2026`; единый генератор исключает неоднозначность, а свежий генератор на операцию делает результат независимым от порядка обработки наборов |
| D-03 | Сортировка ID: строки сравниваются по кодовым точкам Unicode; `class_id` SOP — как целые числа | Порядок сортировки определяет результат перестановки; его нужно зафиксировать |
| D-04 | Границы долей — только целочисленная арифметика: `ceil(20%·n) = (20·n + 99)//100`, `floor(0.25·N) = N//4`, `floor(0.8·M) = (4·M)//5` | Исключает ошибки округления float |
| D-05 | `image_id` — непрозрачный: `"{dataset_id}:{ordinal:06d}"`, порядковый номер по отсортированному `relative_path`. Естественный ключ остаётся в `relative_path` | Имена файлов и каталогов MVTec содержат метку (`good`/тип дефекта); алгоритм не должен видеть метку через идентификатор или путь |
| D-06 | `source_group_id`: KADID — ID оригинала; HPatches — имя последовательности; MVTec — `{категория}/{stem}` исходного изображения; SOP — `class_id` | Единица, внутри которой наблюдения не независимы (ДАН-02, ВОСП-01) |
| D-07 | `dataset_manifest_hash` — SHA-256 от канонической сериализации содержимого таблиц (строки по ключу, колонки в порядке схемы, значения в каноническом JSON), а не от байтов parquet | Байты parquet зависят от версии pyarrow и метаданных записи |
| D-08 | `run_id` детерминирован: `{module}-{profile}-{config_hash[:12]}-s{seed}` | Повторный запуск той же конфигурации с тем же seed — это тот же запуск, поэтому resume работает без дополнительного состояния |
| D-09 | Секция конфигурации `paths` исключена из `config_hash` | Перенос данных на другую машину не должен менять идентичность опыта; идентичность данных обеспечивает `dataset_manifest_hash` |
| D-10 | В `predictions.parquet` добавлена колонка `outcome ∈ {decided, reject, not_applicable}`. Технические ошибки в `predictions` не попадают | ДАН-05: `reject`, `not_applicable`, `null` и ошибка запуска — разные вещи |
| D-11 | Добавлена команда `experiments build-manifests`; `validate-data` только проверяет и не создаёт манифест | Построение манифеста изменяет состояние, проверка — нет; ТЗ перечисляет обязательные команды, но не запрещает дополнительные |
| D-12 | `aggregate` завершается ошибкой, если в `predictions` нет строки для какой-либо пары оцениваемого набора; отсутствие строки не трактуется как отказ | ДАН-05, формула Coverage |
| D-13 | Зависимости сверх списка ОБЩ-02: `pyarrow` (parquet), `PyYAML` (config.yaml), `pytest` (проверки); `psutil` — опционально (пиковая память) | Без них контракт данных не реализуется |
| D-14 | SOP читается из исходной раскладки поставки; TFDS не поддерживается | Исходная раскладка содержит `class_id` и официальное разбиение; поддержка TFDS — отдельное расширение |
| D-15 | Правило порога: `unified_score ≥ threshold` ⇒ `y=1` (совпадение на границе — соответствие). Правило задаётся в конфиге явно (`tie_rule: ">="`) | Граничный случай должен быть однозначным |
| D-16 | Блокировка test реализована через реестр версий протокола и файл `test_opened.json` (раздел 7.5) | ВОСП-04 |
| D-17 | В `pairs.parquet` добавлена необязательная колонка `input_mask_path` — маски, доступные алгоритму по постановке; `gt_mask_path` остаётся только оценочной | ДАН-04 требует различать входные маски и эталонные |
| D-18 | Номера версий библиотек в спеке не фиксируются | Требуется проверочная установка (ОБЩ-02) |
| D-19 | Код платформенно-нейтрален (Linux и Windows): `pathlib`, без жёстко заданных разделителей и абсолютных путей | Раздел 6 ТЗ: код не содержит абсолютных путей разработчика |
| D-20 | Видимость колонок пары для алгоритма задаётся белым списком в конфиге (`inputs.pair_columns`); `y_match`, `gt_H_path`, `gt_mask_path` в нём запрещены | `transform_id` и `severity` могут в некоторых постановках определять метку; решение остаётся за ТЗ программы, но запрет на метку и GT абсолютен |

## Решения P3 (metric)

Спека `TZ_03-metric-proxy-design.md` §2. ★ — проверить в первую очередь.

| ID | Решение | Причина |
|---|---|---|
| M-D01 | `C_tr` — все классы части `train` манифеста; прокси создаются для всех. Семплер использует только классы с ≥2 изображениями (МЕТР-04). Остальные перечисляются в `sampler_exclusions.parquet` с причиной `FEWER_THAN_2_IMAGES` | Г2-150 суммирует по всем `C_tr`; в SOP таких классов, по ожиданию, нет, но правило должно быть однозначным |
| M-D02 | Индекс прокси: `class_id` части `train`, отсортированные как целые числа, → `0…Ncls−1`. Сохраняется в `proxy_index.parquet` (`proxy_idx, class_id, n_images, sampler_eligible`) | МЕТР-02: отдельно сохранить соответствие исходных train-ID непрерывным индексам |
| M-D03 ★ | Состав пакета и параметры аугментаций — чистая функция `(seed, global_step)`: генераторы `expcore.seeding.stream(seed, "sampler", global_step)` и `stream(seed, "augment", global_step)`. Состояние семплера = `(seed, global_step, sampler_version)` | Пакеты λ=0 и λ>0 одинаковы по построению; resume точен без сохранения внутреннего состояния генератора; паритет проверяется сравнением `batches.parquet` |

| M-D05 ★ | Параметры γ/β слоёв BatchNorm backbone обучаются; скользящие mean/variance не обновляются, потому что backbone вызывается с `training=False` | ТЗ замораживает «статистики», остальные веса backbone обучаются |

Изображение читается через `ImageStore.load(image_id, color="rgb")` в uint8; оттенки серого и CMYK приводятся к RGB загрузчиком | Детерминированный CPU-ресайз; явный цветовой порядок (ТЗ00-спека §5.3) |
| M-D07 | Сумма очереди `S_c` хранится в float64, буфер очереди — в float32. Центр `μ̂_c = (S_c / n_c)` приводится к float32 | Снижает дрейф суммы за ~60 тыс. шагов; проверка дрейфа остаётся (§6.6) |
| M-D08 | Норма прокси проверяется так же, как норма эмбеддинга: `‖p_c‖₂ ≤ ε_p` или нечисловое значение → остановка `INVALID_PROXY_NORM`. `ε_p = ε_z = 10⁻¹²` | ТЗ задаёт допуск `ε_p` в Г2-126, но не называет код |

| M-D10 | Запросы без положительного кандидата: `outcome=not_applicable`, `reason_code=NOT_APPLICABLE_NO_POSITIVE_IN_GALLERY` (регистрируется через `register_reason_code`); в `retrieval.parquet` — флаг `no_positive_in_gallery=true`. Они исключаются из знаменателя Recall@k, их число выводится отдельно | МЕТР-03 + ТЗ00 INV-05 требует префикс `NOT_APPLICABLE_` |
| M-D11 | Validation и test: запросы = все изображения части, gallery = все изображения той же части, кроме самого запроса | МЕТР-03 и §7 ТЗ 03; состав gallery одинаков для всех методов |

| M-D13 | Поиск выполняется в NumPy float32 на CPU, блоками `(block_q × block_g)`; бегущий top-k на запрос | МЕТР-06; не зависит от GPU и повторяем |

Критерий `max_recall_at_fpr_le_0.05`: среди порогов с `FPR_all ≤ 0.05` максимальный `Recall_all`; при равенстве — меньший `tD` | Г2-134 + ТЗ 00 |

| Решение | Причина |
|---|---|
| Стадийные запуски: `embed` и `search` обученной модели — отдельные запуски ТЗ 00 (`config_hash` от `base_config_hash` и стадии), `stage.json` указывает стадию и обучающий запуск | Контракт ТЗ 00: один запуск — одна команда; `train` остаётся базовым запуском конфига |
| `predictions.parquet` делится по INV-07: `search --pairs` пишет строки пар, `search` без `--pairs` — строки запросов | Один вид строк на `run_id`/`method_id`; `aggregate` соединяет по `pair_id` |
| Разбор памяти пишется в `memory.json`, а не в `run.json.memory` | Схема `run.json` запрещает лишние ключи |
| `class_subset` — `{n_classes, seed}`, seed подмножества не равен seed запуска | Спека §4.5; иначе seed 11/23/37 учатся на разных подмножествах и среднее настройки смешивает данные |
| `encoder.keras` — backbone → dense без слоя L2; L2 применяет потребитель по `preprocess.json` | Keras 3 не сериализует подклассовый `Encoder` без `get_config` |
| Нетренируемый `embed` (`imagenet_fixed`, `rgb_hist`) — базовый запуск конфига; `--split` необязателен | Так `experiments run` исполняет сгенерированный план E4-fixed |
| Шум E7 — `stream(seed, "degrade", i)`, `i` — позиция изображения в списке запросов | Поток `degrade` добавлен в `expcore` (запрос №4, ветка `tz00-program-hooks`) |
| Resume делят `resume_training` (цикл, состояние) и CLI (`config.resolved.yaml`, проверка каталога checkpoint) | Конфиг и идентичность запуска проверяет ТЗ 00; цикл обучения общий с `run_training` |
| `validate_profile` вызывает `prepare_run` для каждой команды metric | `expcore` его не вызывает; вне smoke веса должны быть `imagenet` с совпавшим `weights_sha256` |
| `.gitattributes`: `configs/metric/** text eol=lf` | Хэш конфига зависит от байтов; CRLF на Windows меняет `config_hash` |
| Конфиги опытов порождает `metric.expconfigs.materialize`, ячейка — один конфиг модуля | `experiments plan` не умеет сетки и подстановку выбранных значений |
| Корневой `conftest.py` изолирует построитель пар P3 в тестах | `pytest tests/unit` должен проходить отдельно; правильное решение — изоляция реестра в фикстуре ТЗ 00 (запрос владельцу) |
| Открытый запрос к ТЗ 00: общий `prepare_run`; №1 и №4 закрыты веткой `tz00-program-hooks` | Не блокирует P3: подготовка повторена в `runctx.py` |
| Pilot на реальном SOP не выполнен (ожидает целевой среды): набор SOP на этой машине отсутствует, TensorFlow 2.21 на нативной Windows без GPU. Оценка GPU-часов §10 остаётся прогнозом, фактических чисел нет | Измерения откладываются; команды ниже |

### Pilot на реальном SOP (ожидает целевой среды)

Не выполнен. Выполнить на Linux/WSL2 с GPU, TensorFlow по `requirements-metric.lock`, SOP в `--data-root`.

1. Манифесты с парами P3: `python -m experiments build-manifests --config CONFIG.yaml`;
   затем `python -m experiments validate-data --config CONFIG.yaml`.
2. Временная копия `configs/metric/cells/e1_tune/train-proxy_cal-lambda0.01.yaml` с `params.train.epochs: 1`, `seeds.seed: 11`, профиль pilot (λ=0,01 и один seed):
   `python -m metric train --config <копия>`.
3. Записать (из `training_steps/`, `epochs.parquet`, `timers.json`, `memory.json`, `best_checkpoint.json`): `step_time_ms`, пик памяти (GPU и процесса), `M_Q`, время эпохи и валидации.
4. Пересчитать оценку GPU-часов §10 по этим числам; до тех пор она остаётся прогнозом.
